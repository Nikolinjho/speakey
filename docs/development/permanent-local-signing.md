# Постоянная подпись локального Keyboop

Локальные сборки используют один сертификат `Keyboop Local Dev` из пользовательской Keychain. Его закрытый ключ создан в Keychain и не экспортировался. Сертификат действует до 27 октября 2036 года, 17:35:50 MSK, разрешает только подпись кода и не является центром сертификации.

SHA-1 сертификата: `749281C2A0E19FC82DA85918A28F5BCC195C5597`. Это публичный идентификатор сертификата.

## Сборка и обновление

```bash
bash scripts/sign-keyboop-app.sh --check-identity
KEYBOOP_BUILD_APP=/private/tmp/Keyboop_local_build.app bash build-app.sh
```

Сборка проверяет сертификат до компиляции, подписывает вложенные компоненты изнутри наружу и проверяет готовый bundle. При отсутствии сертификата, неоднозначном имени или ошибке подписи она завершается с ошибкой. Перехода на ad-hoc нет, `KEYBOOP_SIGN_ID=-` запрещён. Явный `KEYBOOP_SIGN_ID` позволяет выбрать другой сертификат по точному имени или SHA-1, но смена сертификата меняет идентичность приложения.

Рабочая локальная версия остаётся в `/Applications/Keyboop_local.app` с bundle ID `ru.keyboop.app.dev`. Подготовленная копия подписывается до установки. Работающий установленный bundle не переподписывается.

Для следующих обновлений нужно сохранять этот сертификат и ключ, bundle ID и путь приложения. Создание нового сертификата с тем же именем не сохраняет прежнюю идентичность. Публичный PEM в репозитории не заменяет закрытый ключ Keychain.

## Проверки

Два разных скомпилированных бинарника получили разные cdhash, но одинаковые designated requirements с отпечатком сертификата. Оба прошли строгую проверку по требованию первой подписи. [Протокол](artifacts/permanent-signing/identity-proof.json), [публичный сертификат](artifacts/permanent-signing/certificate-public.pem).

Все шесть компонентов настоящего Keyboop подписаны тем же сертификатом. Entitlements локальной версии сохранены, профиль нейронной помощи отключён. [Проверка bundle](artifacts/permanent-signing/staged-app.json). Тринадцать тестов проверяют успешную подпись и остановку при ошибках. Независимое ревью конвейера одобрено.

Строгая проверка выполняется с доступом к пользовательскому доверию Keychain. В изолированной среде тот же сертификат может возвращать `CSSMERR_TP_NOT_TRUSTED`.

При первом переходе с ad-hoc на сертификат потребовалась повторная выдача доступов. Установленный процесс подтвердил AX=true и InputMon=true в 17:41:06 MSK. Полная следующая сборка выполнена обычным `build-app.sh` без переопределения сертификата. После установки в 17:44:18 MSK новый процесс сразу сообщил `launched` с AX=true и InputMon=true, затем `engine STARTED ok (AX=true InputMon=true)` в 17:44:19 MSK. Хеш сборки изменился, designated requirement остался тем же. Повторная выдача доступов для этой сборки не потребовалась.

Проверена строгая подпись установленного приложения, открыто настоящее окно настроек процесса 56093. Все прежние ID наблюдений, случаев и правил журнала сохранены. Режим observe сохранён.
